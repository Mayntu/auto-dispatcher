# Памятка: связать `web/` с бэкендом и проверить

Для агента/разработчика без контекста проекта. Читать в таком порядке:
1. этот файл;
2. `docs/frontend-contract.md` — что отдаёт бэкенд (REST, WS, поля);
3. `CLAUDE.md` — §8 (модели), §15–16 (шина, API), §27 (как должен выглядеть экран для железнодорожников; при расхождении с §18 прав §27).

## Что за проект (в двух абзацах)

«Автодиспетчер» — подсказчик поездного диспетчера однопутного участка (6 раздельных пунктов, 5 перегонов с автоблокировкой).
Бэкенд эмулирует поле (поезда, светофоры, сбои), держит бесконфликтный план (CP-SAT), при сбое за ≤ 5 с предлагает
3 варианта с цифрами, считает индекс качества 0–100, what-if и профили автоведения. Движение непрерывное, график на 48 ч.

Фронт (`web/`, React + Vite) сейчас умеет работать на **встроенном движке** (`web/src/engine/*`, демо без сервера) и в
**live-режиме** через `web/src/api/backend.js` + `web/src/api/adapter.js` (`VITE_DATA_SOURCE=live`). Задача — довести
live-режим до полного: экран целиком на данных бэкенда, на фронте ничего не досчитывать «на глаз» (§24).

## Правила совместной работы (важно)

- **Правишь только `web/`** (и `docs/backend-issues.md`). `app/`, `tools/`, `data/`, `tests/`, `CLAUDE.md` не трогаешь —
  бэкенд параллельно дорабатывает другой агент, правки в двух местах ломают планировщик.
- **Баг или нехватка в бэкенде** → запись в `docs/backend-issues.md`: что сделал (запрос/шаги), что пришло, что ожидал,
  время симуляции. Не обходи баг на фронте подсчётами — сначала запиши.
- Нужно новое поле — тоже в `docs/backend-issues.md` с пометкой «контракт».
- `git pull --rebase` перед работой и перед пушем, коммиты маленькие, только файлы `web/` и `docs/backend-issues.md`.

## Запуск

```bash
# бэкенд (Python 3.12)
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -e ".[dev]"
.venv/bin/python -m app.all            # http://localhost:8000 ; Swagger: /docs ; старый отладочный экран: /
# другой порт: PORT=8001 .venv/bin/python -m app.all

# фронт
cd web && npm install
echo "VITE_DATA_SOURCE=live" >> .env    # + VITE_BACKEND_URL=http://localhost:8001, если порт другой
npm run dev                             # http://localhost:5173, /api и /ws проксируются на бэкенд
```

Быстрая проверка, что бэкенд жив: `curl localhost:8000/health`, `curl localhost:8000/api/state | head -c 500`.
Авторизации в бэкенде сейчас нет (MVP): логин на фронте можно оставить локальным.

## Как проверять (сценарии диспетчера)

Для каждого пункта: сделать в UI → сверить с `GET /api/state` (цифры на экране = цифры бэкенда).

1. Старт: план v1, индекс «Норма» (≥ 90), на ГИД 6–14 ниток, безопасность 0, есть пакеты попутных поездов.
2. Скот на перегоне `R1-STP` км 24.5, 15–30 мин → за ≤ 5 с три карточки, одна «рекомендуем», время ×1, призраки на ГИД.
   Применить рекомендуемую → новая версия плана, карточки ушли в журнал, скорость вернулась.
3. Применить вариант через минуту раздумий → либо применяется, либо 409 «устарел» и сами приходят новые карточки.
4. Неисправность 2003 на `STP-R2` → среди карточек «Вспомогательный локомотив»; строка «если сбой затянется» есть.
5. Снять последний сбой → «Активных решений нет» (или одна карточка «Возврат к графику»).
6. Отклонить все карточки → план прежний, в журнале «отклонено».
7. Поезд перед красным проходным на мнемосхеме стоит, блок-участки красные под поездом, стрелка направления перегона
   соответствует идущему поезду.
8. 8 сбоев подряд → UI не тормозит, p95 доставки WS < 500 мс (`{"op":"latency","p95_ms":N}` раз в 5 с на сервер).
9. Перезагрузка страницы посреди сбоя → тот же экран из WS `snapshot`.

Автоматическая проверка бэкенда через тот же API (полезно как образец запросов): `tools/e2e_dispatcher.py`.
