Код: `main` @ `4387dda` + исправление выбора поезда в сценариях (см. «Отступления»). Дата: 2026-10-02.

Скорость (A, D) мерилась на свободной машине; надёжность и эффект (B, C) — параллельно с другими прогонами (на них
время не влияет: решатель в стрессе детерминированный по «рабочим единицам», а не по секундам).

## 2. Как мерили и как повторить

```bash
python -m tools.pitch_numbers --part untimed     # E: факты, размер модели, тесты; C8: энергия автоведения
python -m tools.pitch_numbers --part timed       # A: скорость; D: демо (только на свободной машине!)
python -m tools.stress --runs 120 --seed0 120 --procs 4 --json R.json                              # B
python -m tools.stress --runs 30 --seed0 120 --procs 2 --policy ignore   --pins off --json B.json  # C: база
python -m tools.stress --runs 30 --seed0 120 --procs 2 --policy balanced --pins off --json S.json  # C: система
python -m tools.pitch_report --reliability R.json --base B.json --balanced S.json                 # сводка в JSON
```

- **A1 (сбой → 3 варианта).** 54 сбоя шести типов (препятствие, неисправность поезда, окно, предупреждение, опоздание поезда, отказ светофора) на стресс-сидах 120–173, в случайный момент 15–150 мин после старта. Тот же код, что в сервисе: пул из 3 процессов, 3 стратегии параллельно, оценка карточек. Плюс 12 сбоев через живой сервис: от `POST /api/incidents` до прихода `planner.variants` в WebSocket (включает debounce 300 мс).
- **A2.** 30 случайных точек будущих стоянок в живом сервисе, время по часам клиента по HTTP на localhost.
- **A3.** 5 WS-клиентов, 60 с: время получения минус `ts_wall` конверта (ставится при публикации) — это верхняя оценка серверной части (шина + API + отправка + цикл клиента).
- **A4.** Сценарий `mass_incidents` (8 сбоев за 2 мин симуляции), 5 WS-клиентов; пока висят карточки, время идёт ×1, поэтому 8 сбоев приходят примерно за 2 реальные минуты.
- **B5.** `tools/stress.py`: случайные сбои × 5 моделей поведения диспетчера (применяет лучший / поздно / худший / игнорирует / перепланирует), каждые 7-е — массовые сбои, каждый 3-й — диспетчер ещё и задерживает поезда указаниями на ГИД; окно 8,5 ч на сид. Решатель в стрессе — 1 поток и «детерминированное время», чтобы сид воспроизводился.
- **C6–C9.** На одних и тех же 30 сидах и сбоях: **база** = порядок плана сохраняется, времена протягиваются (тот же `refresh`, что в сервисе), варианты не применяются; **система** = диспетчер сразу применяет «Минимум задержек». Опоздание — фактическое время прибытия на конечную в поле минус график, для всех поездов, прибывающих по графику до конца окна минус 2 ч (14 поездов на сид); ещё не прибывшие — опоздание на момент конца. Указания на ГИД в этом замере выключены (они задерживают поезда намеренно).
- **C8.** 10 сидов × 8,5 ч без сбоев, каждые 10 мин — профиль автоведения на ближайший перегон каждого поезда (1050 профилей); «с запасом времени» — плановое время хода больше минимального более чем на 5 с (510 профилей). Энергия — модель `railcore/eco.py`.
- **D.** Последовательность §19 с сидом 2026 (готового сценария `demo_full` нет — см. «Нет данных»).

## 4. Что хуже цели (не прячем)

1. **Отклик экрана на фронте — нет надёжных данных, возможно, хуже цели.** Фронт сам отчитывается p95 «от публикации до отрисовки»: в первой сессии было **1 328 мс**, позже — **58 884 мс** (оба замера с вкладки при параллельной нагрузке; браузер сильно тормозит отрисовку во фоновой вкладке). Серверная доставка — 2,5 мс, значит, задержка на стороне браузера. Нужно перемерить с вкладкой на переднем плане на свободной машине и, если останется ≥ 500 мс, разбираться в отрисовке ГИД.
2. **Пересчёт при сбое под нагрузкой.** На свободной машине p95 3,6 с (цель ≤ 5 с — выполнено), но живой сценарий, запущенный одновременно с 6 процессами стресса, показал 6,6 с для пачки из 8 сбоев. На демо машину ничем не нагружать.
3. **Fallback решателя в 2,1% решений** (65 из 3 042 в стресс-прогонах, 3 из 162 в A1): за отведённое время CP-SAT не нашёл решение, показана протяжка без смены порядка (честно помечено в карточке). Самое долгое решение в стрессе — 19 с, но это стресс-режим (1 поток, «детерминированное время», машина под нагрузкой); в сервисе лимит 3,5 с по часам, максимум в живых замерах — 3,9 с.
4. **Незапланированных остановок на 13% больше, энергии тяги на 2,6% больше** у системы против базы: чтобы развести скрещения, план чаще ставит поезд на разъезд. Опоздания при этом −41…−44%.
5. **2 сида из 30 — опоздания с системой больше, чем без неё** (жадное «применить «Минимум задержек» сразу» не всегда лучше на горизонте 8,5 ч).
6. **Демо: препятствие в 08:00 ничего не показывает** — ставить в 08:15 (см. D10).
7. **Правдоподобие для экспертов:** в объяснении карточки «Пассажирский 341 ждёт на Ст. Степная 28 мин, пропуская грузовой 2002» — длинная техническая стоянка пассажирского в нормативном графике (его разводит CP-SAT без запрета на такие стоянки). Железнодорожники могут задать вопрос; стоит ограничить стоянку пассажирских в генераторе графика.

## 5. Нет данных

- **`demo_full` как готовый сценарий** не реализован — последовательность §19 прогнана скриптом (`tools/pitch_numbers.py --part demo`).
- **Отклик рендера фронта** — см. п. 1 выше: метрика есть, надёжного замера нет (нужен браузер с вкладкой на переднем плане; расширение браузера для автоматизации в этой сессии не было подключено).
- **RabbitMQ, БД, PDF-отчёт** — не реализованы, поэтому и не измерялись.

## 6. Отступления от задания

- **Изменён код продукта в одном месте (не ради цифр, а исправление бага):** `app/field/scenarios.py` — сценарий «8 сбоев» пропускал шаг «опоздание поезда», если в этот момент ни один поезд не стоял на станции, и создавал 7 сбоев вместо 8. Теперь берётся поезд на перегоне или ближайший к отправлению. Замер A4 сделан уже с исправлением (создано 8 из 8).
- `tools/stress.py` дополнен (только инструмент): политика для всех сидов, отключение указаний, фактические опоздания на конечных, энергия, внеплановые остановки, индекс, счётчик fallback, выгрузка в JSON. Поведение без новых флагов прежнее.
