# Автодиспетчер

Консультативная система поддержки решений поездного диспетчера однопутного участка в контуре ДЦ.
Строит бесконфликтный график, при сбое за доли секунды предлагает 2–3 плана с цифрами последствий и объяснением,
даёт машинисту рекомендованный профиль скорости и позволяет моделировать «что будет, если».

> Прототип для хакатона РЖД. Только mock-данные; не заменяет СЦБ, АЛСН/АЛС-ЕН и другие системы безопасности.

## Запуск

```bash
npm install
cp .env.example .env      # задайте логины/пароли
npm run dev               # http://localhost:5173
npm run build             # production-сборка в dist/
```

Учётные записи берутся только из переменных окружения (`VITE_DISPATCHER_*`, `VITE_INSTRUCTOR_*`, `VITE_ADMIN_*`).
## Роли

| Роль | Что делает в системе | Права |
|---|---|---|
| Диспетчер | следит за участком, видит ситуацию и выбирает вариант исхода при сбое, запускает what-if, смотрит профиль скорости, историю и отчёты | Работа с участком |
| Инструктор | на своей карте создаёт нештатные ситуации, уточняет их длительность и отмечает устранение, управляет временем симуляции | Сценарий учений |
| Администратор | всё, что у диспетчера, плюс веса и пороги индекса, приоритеты категорий поездов, параметры оптимизации | Работа с участком + Настройки |

Роли и права описаны в `src/engine/roles.js`. Права проверяет сам движок, а не только интерфейс: попытка действия без права
отклоняется и попадает в журнал. Машинист — не пользователь системы, а получатель рекомендаций (карточка поезда).

## Два экрана: инструктор и диспетчер

Откройте приложение в двух окнах или вкладках одного браузера (например, на двух мониторах) и войдите под разными
ролями. Экраны синхронизируются через `BroadcastChannel` (`src/engine/sync.js`): симуляция идёт на одном ведущем экране,
остальные зеркалят его состояние и отправляют свои действия командами. Если ведущий экран закрыть, его роль перейдёт
к оставшемуся.

**Инструктор** перетаскивает события на свою карту (скот, закрытие пути, сбой сигнала — на конкретный путь перегона;
поломка, опоздание — на поезд), выбирает начало и длительность, управляет временем и видит решения диспетчера.

**Диспетчер** событий не создаёт. При сбое статус становится красным, на карте пульсируют будущие конфликты, а слева
появляются варианты исхода — как маршруты в навигаторе. Сверху выбирается, что важнее («Сбалансированно», «Меньше
опозданий», «Пассажиры вовремя», «Экономия энергии», «Надёжнее»); у каждого варианта — «Когда выбирать», «Плюсы»,
«Минусы» и что изменится. «Применить план» — маршруты для ДЦ выставляются автоматически.

**Карта.** Станции — овалы с путями внутри: занятый путь светится цветом стоящего поезда, кольцо вокруг показывает
заполненность станции, голубой ореол — скорое прибытие; в подписи — «занято 1/4 · → 701 в 08:28». Перегоны — по два
пути со съездами (X); каждый путь окрашен по загруженности, как пробки. Поезда — составы, плавно едущие вдоль пути.
Клик по поезду — маршрут до конца участка с временем прибытия и карточка с рекомендацией машинисту.

**Поездограмма** — сворачиваемая панель под картой: линия — поезд, бледный пунктир — нормативный график,
перекрытия — заштрихованные зоны; перетаскивание сдвигает время.

## Данные

Участок описывается таблицами БД (mock — `src/data/network.js`):

| Таблица | Поля | Что это на схеме |
|---|---|---|
| `nodes` | id, pos_x, pos_y, tracks_amount | станции и разъезды — по координатам, с числом путей |
| `edges` | id, start_node_id, end_node_id, length, tracks_amount | перегоны; пока оба пути свободны, встречные не конфликтуют |
| `turnouts` | id, edge_id, pos | стрелки; на двухпутке — перекрёстные съезды (X) между путями |
| `blockages` | id, edge_id, pos_start, pos_end | перекрытия — так сохраняется событие, брошенное на перегон |

Названий узлов и допустимых скоростей в схеме нет — они лежат рядом в небольшом справочнике. Чтобы перекрытие
хранило, какой из двух путей закрыт, в `blockages` нужно поле с номером пути (в прототипе — `track`).

Скорость модельного времени — ×1 / ×20 / ×60 в шапке, факторы индекса — по клику на индекс. Если решение не принято,
а до первого конфликта осталось меньше `autoApplyLeadSec`, система применяет безопасный вариант «Ждать устранения».

## Как это устроено

```
src/
  core/        чистая доменная логика (без React/DOM) — переносится на backend как есть
    section.js        участок из таблиц nodes/edges/turnouts, 10 поездов 4 категорий
    scheduler.js      автодиспетчеризация: последовательное резервирование + фиксированная очерёдность
    planner.js        стратегии, оптимизатор очерёдности, генерация вариантов и объяснений
    conflicts.js      CDR: встречные на перегоне, интервал попутных, ёмкость путей; скрещения, стоянки
    qualityIndex.js   индекс I = 100·Σwᵢsᵢ по пяти факторам
    profile.js        автоведение (eco-driving): разгон → движение → накат → торможение
    disruptions.js    фиксация сбоя и привязка к поездам
    routes.js         план → маршруты приёма/отправления для ДЦ
    eventBus.js       шина событий
  engine/      оркестратор: эмулятор ДЦ, журнал, решения, what-if, история, отчёты
    planner.worker.js расчёт вариантов в отдельном потоке
  components/  интерфейс: мнемосхема, варианты, карточка поезда, панели
  data/        mock-данные в формате БД
docs/          архитектура
```

Подробно — [docs/architecture.md](docs/architecture.md).

### Алгоритм в двух словах

- **Модель альтернативного графа.** Каждый конфликт за перегон или путь — выбор «кто первый». Оптимизатор перебирает
  очерёдность поездов (локальный поиск: перестановки соседей и «вперёд»), каждый порядок разворачивается в график
  последовательным резервированием перегонов и путей. Критерий — взвешенная по категориям задержка плюс штрафы за конфликты.
- **Защита от встречных тупиков.** Поезд не отправляется на перегон, если на следующем раздельном пункте не будет свободного
  пути — откат назад. Если путь занят ещё не спланированным поездом, сначала планируется он.
- **Скользящий горизонт.** Всё, что произошло до текущего момента, заморожено; пересчёт идёт от «сейчас» при каждом событии,
  уточнении длительности и устранении сбоя.
- **Неопределённость.** Сбой задаётся диапазоном (например, 20–45 мин). План строится по ожидаемой длительности
  (настраивается), а для каждого варианта считается индекс при худшем сроке.
- **Автоведение.** Для каждого перегона между остановками подбираются скорость движения и точка начала наката так,
  чтобы прибыть по графику с минимальной работой тяги.

### Индекс качества движения

| Фактор | Как считается |
|---|---|
| Соблюдение расписания | 1 − (ср. взвешенное опоздание / норма), веса — по категориям |
| Пропускная способность | нормативное время хода / плановое; отменённые поезда — потеря |
| Энергоэффективность | энергия нормативного графика / энергия плана при автоведении |
| Конфликты | 1 − 0,25·конфликты − 0,04·вынужденные стоянки сверх норматива |
| Точность прибытия | доля плановых прибытий в пределах ±3 мин |

Категории по умолчанию: «Норма» ≥ 80, «Внимание» 60–79, «Критично» < 60. Веса и пороги меняются в настройках без перезапуска.

## Метрики (замер на обычном ноутбуке)

| Требование | Цель | Факт |
|---|---|---|
| От события до готовых вариантов | ≤ 5 с | ~10–20 мс расчёт, < 100 мс с доставкой из Worker |
| Конфликтов в принятом плане | 0 | 0 (детектор конфликтов проверяет каждый вариант) |
| Обновление экрана после события | < 500 мс | прогноз и конфликты — сразу, расчёт вне основного потока |
| 8 сбоев одновременно | без просадки | ~12 мс расчёт, вне основного потока |
| Частота телесигнализации | ≥ 1 раз/с | 4 раза/с |

## Что дальше

- Вынести `src/core` + `src/engine` в backend-сервис на Node без изменений с REST/WebSocket, описать OpenAPI.
- Хранение истории в БД (TimescaleDB / ClickHouse) вместо памяти браузера.
- Точная тяговая модель (профиль пути, кривые, тяговые характеристики серии локомотива).
- Метод ветвей и границ / MILP для точного решения альтернативного графа на больших участках.

## Работа с бэкендом команды

Интерфейс работает в двух режимах:

- **Демо** (по умолчанию) — встроенный движок считает план и варианты прямо в браузере, сервер не нужен.
- **С сервером** — данные идут с бэкенда по протоколу ТЗ (§15–16): REST `/api/...` и поток событий WebSocket `/ws`.

Включить работу с сервером — в `.env`:

```
VITE_DATA_SOURCE=live
VITE_BACKEND_URL=http://localhost:8000   # куда dev-сервер проксирует /api и /ws
VITE_API_BASE=/api                       # префикс REST (в ТЗ — /api/v1)
VITE_SIM_EPOCH=07:55                     # SIM_EPOCH сервера, если он не присылает его в снимке
```

Что берётся с сервера: участок (`GET /infra`, однопутка с автоблокировкой), расписание, план, варианты, сбои,
положение поездов и сигналы (`field.state`), индекс (`kpi.index`), what-if, профили автоведения (`GET /ato/{поезд}`).
Кнопки интерфейса вызывают `POST /plan/apply` (устаревший вариант — 409, «пересчитываю варианты»),
`/incidents`, `/incidents/{id}/resolve|estimate`, `/sim/clock`, `/whatif`, `/whatif/{id}/promote`, `/scenarios/{id}/run`.

Весь разбор формата сервера — в одном файле `src/api/adapter.js`: если поле на сервере называется иначе, правится только он.
Режим работы с сервером — `src/engine/live.js`, клиент — `src/api/backend.js`.
